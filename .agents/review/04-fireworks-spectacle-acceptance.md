# 烟花爆炸绚烂度（更多粒子 / 更长尾迹 / 更大密度 / 更大范围）实施与验收记录

> 范围：`src/fireworks.ts` 的爆炸与尾迹数值基线（spec 01 §7.4），不含文字采样与收尾逻辑。
> 结论边界：**自动化契约通过（55/55，与改动前同数）；线上部署与 HTTP smoke 已完成；人工视觉矩阵与真机帧时间未执行**。
> 本文不把"测试通过"当作视觉验收通过：本文记录的是**新数值基线**，观感是否达标仍需产品所有者目视确认。
> 设备/浏览器：未启动浏览器观察画面；粒子负载用 Node 直跑 `createWorld/update`（无 DOM、无 Canvas 绘制）测量，
> 因此只有"粒子数/几何"是实测值，**帧时间与绘制观感是推理值**。

## 2. 实测数据（Node 直跑模拟，1440×900，种子 240520）

单朵爆炸（同一种子、同一发射点，取 t+0.8s 的径向分布）：

| 指标 | 旧 | 新 | 变化 |
| --- | --- | --- | --- |
| 火花数 | 170 | 248 | ×1.46 |
| 中位半径 | 82px | 79px | ≈持平（内核环把粒子留在环心） |
| p90 半径 | 139px | 165px | ×1.19 |
| 最大半径 | 175px | 227px | ×1.30 |

→ 面积变大（更大范围）而中位半径不后退：环心密度约 ×1.46（相同中位半径下粒子更多）。

24s 连点负载（信号：`maxNonText` = 非文字粒子峰值，`超限` = `maxNonText + text > cap`，超限后由 `enforceCap` 裁掉最老的 trail/spark/ember）：

| 场景 | 旧（cap 1200） | 新（cap 1800） |
| --- | --- | --- |
| 2 次/秒、文字 700 点 | nonText 684 + 700 = 1384 → **超限裁剪 ~184** | nonText 1098 + 700 = 1798 → **不裁剪**（恰好压在 cap 上） |
| 3 次/秒、文字 700 点 | nonText 908 → 超限裁剪 ~408 | nonText 1317 → 超限裁剪 ~217 |
| 5 次/秒、文字 700 点 | nonText 1117 → 超限裁剪 | nonText 1656 → 超限裁剪 |
| 尾迹峰值（2 次/秒 / 5 次/秒） | 89 / 215 | 163 / 397 |
| 2 次/秒、低动态 | cap 420、文字 230 点：nonText 323 + 230 = 553 → 裁剪 ~133（-24%） | cap 640、文字 350 点：nonText 478 + 350 = 828 → 裁剪 ~188（-23%） |
| `update()` 纯逻辑耗时 | 0.03–0.04ms/帧 | 0.05–0.06ms/帧 |

结论：**新增粒子对 JS 物理成本几乎无影响**（每粒子 O(1)，`update` 差值 ≈ 0.015ms/帧）；
真正的成本是 `render` 的 `fillText` 调用数（峰值 ×1.5，最坏帧 ≈1800 次 + 状态切换）。这是本轮唯一未实测的风险项。

可接受的中间档：3 次/秒起 `enforceCap` 开始裁剪装饰烟花（by design）；低动态档的裁剪比例（-23%）与旧档（-24%）一致，
说明 640 这个新值没把低动态挤得更紧。任何裁剪强度下 text/rocket 都不被裁剪，文字始终补齐（实测 700/700、990/990）。

## 3. 预算与上限评估（是否需要联动 `PARTICLE_CAP`/`TEXT_SHARE`）

- **必须联动 `PARTICLE_CAP`**：旧 cap 1200 下，2 次/秒 + 700 点文字就会触发 `enforceCap` 裁剪 184 个粒子，
  即"更多粒子"在常见连点强度下会被上限吃掉，看不到效果。1800 与单朵火花数同为 **1.5×**，比值不变。
- **`TEXT_SHARE` 保持 0.55**：文字上限 660 → 990，装饰余量 540 → 810，**比例不变**（约 2.4 朵爆炸的在途量），
  故不需要动；改它会同时移动文字密度与装饰余量两个坐标系。
- **`REDUCED_CAP` 420 → 640**（0.356 × cap，与原 0.350 一致）：低动态下爆炸火花已 ×0.4；实测裁剪比例与旧档持平（-23% vs -24%）。
- **副作用（需目视复核）**：`budget = floor(cap * TEXT_SHARE)` 上升后，长文案的 `k` 自适应（`planCellScale`）
  更少触发 → 单元更小、ASCII 更密。方向与 rev1 的"增加 ASCII 密度"一致，但**把可读性问题推到更长文案上**：
  990 点上限下"3 行 × 60 字"仍未人工判定（spec 02 §12 第 3 行的判定条件已同步为 990/352）。
- **回退路径**：观感或帧时间不达标时，先回 `BLAST_SPARKS_BASE`/`BLAST_SPARKS_SPREAD`（110/70），
  再回 `PARTICLE_CAP`/`REDUCED_CAP`（1200/420）；四个常量与 spec 02 §3.2 表都在同一处，无需改结构。

## 8. 回写（2026-09，双壳层「空心圈」修复）

产品所有者截图（`屏幕截图_20260918_184102.webp`）显示：爆炸中心是一个约 40px、环心全空的
细圈，而非设计意图的「花心」。根因：内核壳层由 `explode` 传**单一速率**给 `emitSparks`
（`speed` 选项为单值），于是 35% 的粒子全部落在同一半径上（实测速率档只有 1 档）。

修改：

| 项 | 旧 | 新 |
| --- | --- | --- |
| 内核速率 | `100 × 0.45 × (0.8 + rng()×0.4)`（整朵同值，36–54px/s） | 逐粒子 `[0.1, 0.9] × SPARK_SPEED_MIN`（10–90px/s） |
| `SparkOptions.speed` | `number`（整朵同速） | `number \| [min, max]`；单值不抽骰，收尾小烟花的细环保持不变 |
| 常量 | `BLAST_CORE_SPEED_MUL = 0.45` | 删除 → `BLAST_CORE_SPEED_MIN/MAX = 0.1/0.9` |

验证：`node --test` 中「爆炸火花数…内核盘」新断言（内核速率 ≥ 4 个 20px/s 档、最慢 ≤ 0.3×、
最快 ≥ 0.7× `SPARK_SPEED_MIN`）；旧实现副本（`/tmp/oldsrc`，内核回单速）上速率档只有 1 档 → 断言失败，
证明该检查有区分力。另用 ASCII 网格离屏渲染（`/tmp/render.ts`，3px/格）目视对照：修前中心是空心环，
修后中心被粒子填满。
