# ASCII Firework v1 验收评审

> 评审对象：`src/main.ts`、`src/fireworks.ts`、`src/scene.ts`、`src/scene.test.ts`、`src/style.css`、`index.html`、`public/_headers`、工程配置与线上站点。
> 上游文档：`.agents/design/01-product-and-architecture.md`、`.agents/spec/01-ascii-firework-v1.md`。
> 评审时工作副本含未提交改动（`src/main.ts`、`src/fireworks.ts` 的格式化与 `kEff = 26` 调整），评审基于当前工作副本状态。

## 结论

**有条件通过，不建议目前标记为“完整验收”。**

工程、构建、部署和主体架构质量良好；线上产物与本地 `dist` 完全一致。但存在 **3 个明确代码缺陷、2 个移动端/可访问性风险，以及核心真机验证缺口**。修复“必须改”项并完成至少一台真机验证后，可接受为 v1。

---

## 1. 产品体验

### 1.1 揭示稳定时间 3.85s 略慢，但不算阻塞

- **现象：** Spec 的动画基线是 3.2s，实际要等所有粒子进入 `0.8px` 阈值，约 3.85s 才显示重播按钮和写入 `#live`。相关位置：`src/fireworks.ts:75,302-334`。
- **影响：** 3.85s 作为一次性的情绪铺垫可以接受；真正的问题是稳定时间依赖文字长度、视口和随机配对，极端场景可能超过 3.85s。
- **建议动作：** 不继续调高弹簧系数。增加约 `3.8–4.0s` 的硬截止时间，到点后吸附剩余粒子，保证视觉和辅助技术获得确定完成时间。
- **优先级：中｜可以更好**

### 1.2 七次阈值合理，不建议改

- **现象：** 以完成爆炸数而不是点击数计数；第七次爆炸后揭示。
- **影响：** 用户确实参与了体验，节奏明确，也保留惊喜。改成时间或进度条反而会削弱仪式感。
- **建议动作：** 保持七次，不增加可见计数器，也不开放用户配置。
- **优先级：低｜当前正确，无需改**

### 1.3 空文案不揭示的产品取舍正确，但边界实现有缺陷

- **现象：** 空文案时可以无限自由放烟花，分享按钮要求先填写祝福。
- **影响：** 不会用默认文案冒充创建者心意，行为正确。
- **建议动作：** 保留该决策；但必须修复“已经放过七次后再输入文案会立即在对话框背后揭示”的问题，见 §3.2。
- **优先级：高｜产品决策正确，边界必须改**

### 1.4 独立粒子的 ±1.5px 呼吸会损害小字号文字

- **现象：** `src/fireworks.ts:627-631` 给每个粒子不同相位的 ±1.5px 垂直位移。最小文字粒子字号约为 5px 时，位移可达字号的 30%。
- **影响：** 短祝福、大字号下很好看；长中文或三行小字号时更像“抖动”，可能破坏笔画连续性。
- **建议动作：** 优先把幅度降到 `0.6–1px`，或按 `textSize` 比例封顶；更好的“呼吸”是整段文字共享相位，而不是每个点独立摆动。
- **优先级：中｜可以更好**

### 1.5 最长文案的成字可读性尚未验收

- **现象：** URL 测试覆盖了 60 字，但视觉验收似乎只覆盖短祝福。普通模式最多约 840 个文字点。
- **影响：** 三行、60 个中文字符平均每字只有约 14 个点，复杂汉字可能无法辨认。
- **建议动作：** 增加一条手动极限用例：手机竖屏下三行、60 个复杂中文字符。若不可读，应降低产品允许长度，而不是继续提高 1200 粒子上限。
- **优先级：中｜必须补验，是否改代码取决于结果**

## 2. 数值与手感

### 2.1 爆炸数量、寿命和 1200 上限整体合理

- **现象：** 单次爆炸 56–89 个粒子，reduced motion 为 22–35 个；普通粒子寿命 1.1–2.2s，文字最多占上限的 70%。
- **影响：** 七次正常操作不会轻易触顶；稳定文字仍给背景烟花留出约 30% 空间。较早烟花自然熄灭，最后几次烟花承担主要汇聚效果，符合观感。
- **建议动作：** 暂不调整爆炸粒子数、寿命或 1200 上限。真机帧率没有数据前，不要凭桌面体验调参。
- **优先级：低｜当前正确，无需改**

### 2.2 尾迹实际是“最多 50/s”，不是稳定 50/s

- **现象：** `TRAIL_INTERVAL = 0.02`，但 `src/fireworks.ts:244` 每帧最多生成一个尾迹。60fps 时接近 50/s，30fps 时最多约 30/s。
- **影响：** 这是自然的性能降级，低帧率设备反而减少粒子负担；不是需要修复的手感问题，但与 spec 的固定“50/s”表述不完全一致。
- **建议动作：** 更新 spec 为“最多 50/s，受帧率限制”。不要改成 `while` 补齐尾迹，否则卡顿帧后会集中生成粒子。
- **优先级：低｜文档可以更好，代码无需改**

### 2.3 最值得调的只有两个参数

- **现象：** 当前可调项很多，但没有证据表明爆炸数量或重力有问题。
- **影响：** 同时调整多项会难以判断手感变化来源。
- **建议动作：**
  1. 增加揭示硬截止时间；
  2. 降低稳定文字呼吸幅度。  
  其他参数保持不动，等待真机帧率和用户观感反馈。
- **优先级：中｜可以更好**

### 2.4 粒子上限并非绝对上限

- **现象：** `enforceCap()` 不淘汰 `rocket` 和 `text`，所以大量并发火箭时总数可暂时超过 1200。
- **影响：** 正常人工输入很难造成问题；自动重复事件或极端多点触控可能突破预算。
- **建议动作：** v1 不必增加复杂限流。真机发现输入洪泛卡顿时，只在 `launch()` 增加一个简单的活动火箭数上限。
- **优先级：低｜当前可接受**

## 3. 健壮性与边界

### 3.1 `hashchange` 会泄露新链接的祝福并继承旧进度

- **现象：** `src/main.ts:399-401` 收到新 Fragment 后只调用 `commitScene()`，不重置 `blasts`、粒子或页面状态。若旧场景已稳定，新祝福会立即重排并写入 `#live`；若旧场景已有七次爆炸，新祝福会立即揭示。
- **影响：** 在同一标签页打开第二个分享链接时，收件人不需要再放七次烟花，破坏核心产品流程。当前提交描述中把“立即换成第二份祝福”当作正确结果，实际上与设计冲突。
- **建议动作：** 把外部 Fragment 导航视为新场景：读取并应用场景后调用完整重置。编辑器内部的 `replaceState` 不触发 `hashchange`，不会受影响。
- **优先级：高｜必须改**

### 3.2 放过七次后开始输入文案，会在编辑器背后立即揭示

- **现象：** 空文案时 `advance()` 保持 `playing`，但 `world.blasts` 会继续增长。`src/main.ts:326-334` 输入第一个字符后立即更新内存中的 `scene.message`，下一帧便满足 `blasts >= 7`。
- **影响：** 创建者还在输入时，成字动画已经在模态框背后播放；关闭对话框后可能直接看到稳定文字。
- **建议动作：** 当文案从空变为非空时重置世界和爆炸计数；至少保证创建新祝福必须重新完成七次烟花。
- **优先级：高｜必须改**

### 3.3 重播后爆炸声音不再播放

- **现象：** `toPlaying()` 重置了 `world.blasts`，但没有重置 `heardBlasts`（`src/main.ts:110-117,135-140`）。第一次揭示后两者约为 7；重播后前七次爆炸都不满足 `world.blasts > heardBlasts`。
- **影响：** 开启声音后，第二轮烟花只有升空声，没有爆炸声。
- **建议动作：** 把 `heardBlasts = 0` 纳入完整重置。顺便决定是否让 `resetScene()` 重置世界 RNG；如果“重新播放”表示从种子重新开始，就应重置。
- **优先级：高｜必须改**

### 3.4 场景种子没有完全随重播和 `hashchange` 重置

- **现象：** `resetScene()` 不重置 `world.rng`；`jitterRng` 在首次加载时创建为 `const`，更换种子后仍使用旧随机序列。
- **影响：** 新 Fragment 或重播虽然显示新种子，但键盘发射位置和后续随机序列不完全对应该种子。
- **建议动作：** 明确语义。若种子代表场景可复现性，重播和外部场景切换都应重新创建两个 RNG；若只代表初始风格，则在 spec 中写清楚。
- **优先级：中｜可以更好**

### 3.5 `readSceneFromHash` 的回退粒度合理

- **现象：** 未知版本整场回退；当前版本的非法文案、配色和种子逐字段回退。
- **影响：** 一个损坏字段不会抹掉其他有效祝福信息，同时未知版本不会被错误解释。
- **建议动作：** 保持当前实现。12 项测试已覆盖主要字符、长度和字段边界。
- **优先级：低｜当前正确，无需改**

### 3.6 输入裁剪会跳光标，也缺少 IME 边界处理

- **现象：** `src/main.ts:326-331` 一旦裁剪就重新赋值 `msg.value`，光标落到末尾；没有检查 `InputEvent.isComposing`。
- **影响：** 在中间粘贴、编辑超长文本或使用中文输入法接近 60 字边界时，输入位置可能突然变化，组合输入可能被打断。
- **建议动作：** 最低限度跳过 `isComposing` 的 input，在组合结束后裁剪；裁剪时保存并恢复 `selectionStart/selectionEnd`。不要引入复杂表单库。
- **优先级：中｜可以更好，中文真机验收前建议处理**

### 3.7 Resize 会重复分配全屏离屏 Canvas

- **现象：** `resize` 和 `orientationchange` 都直接调用 `setViewport()`；在 revealing/settled 阶段，每次都会创建离屏 Canvas、`getImageData()`、重新采样并吸附。
- **影响：** 移动浏览器地址栏、软键盘和旋转可能连续触发 resize；桌面 1920×1080 每次采样要读取约 8MB 像素数据，可能产生明显卡顿和 GC。
- **建议动作：** 忽略尺寸未变化的事件，并用单个 `requestAnimationFrame` 合并 resize；通常可以删除重复的 `orientationchange` 监听。
- **优先级：中｜可以更好，真机旋转前建议处理**

### 3.8 重播按钮焦点与 Space 暂无确证缺陷

- **现象：** 点击或键盘激活重播后，按钮被设为 `hidden`，代码没有显式安排焦点。
- **影响：** Chromium 通常会把焦点退回 `body`，随后 Space 能继续发射；不同移动/桌面浏览器是否一致尚未验证。
- **建议动作：** 先补桌面键盘矩阵。如果发现焦点仍停留在隐藏按钮，只需在重置时 `replay.blur()`，不要为此建立焦点管理器。
- **优先级：低｜补验即可**

## 4. 可访问性

### 4.1 `#live` 写入时机正确

- **现象：** 只有粒子稳定后才把完整祝福写入 `aria-live`；正常模式约 3.85s，reduced motion 为约 0.8s。
- **影响：** 不会提前向屏幕阅读器泄露惊喜，也不会逐字符制造大量播报。
- **建议动作：** 保持一次性写入，配合揭示硬截止时间即可。
- **优先级：低｜当前正确，无需改**

### 4.2 Reduced motion 未证明能让视力用户完整读出最长祝福

- **现象：** Reduced motion 的总粒子上限为 420，文字最多约 294 个点；`#live` 始终是 `.sr-only`。
- **影响：** 三行、60 个中文字符可能无法仅靠 294 个点辨认。屏幕阅读器用户能听到，但使用 reduced motion 的视力用户未必能看清，尚不能宣称“完整获知祝福”。
- **建议动作：** 在 reduced motion 下，稳定后把 `#live` 同时作为可见文字覆盖层展示，或至少用最长中文文案证明粒子文字可读。可见 DOM 文本是更稳、更简单的方案。
- **优先级：高｜必须改或补充有说服力的实测**

### 4.3 `body { touch-action: none }` 会阻止页面缩放

- **现象：** `src/style.css:37` 对整个 body 禁止触摸手势，Canvas 自身又在 `:59` 单独设置了一次。
- **影响：** 用户无法双指缩放；对低视力用户不友好，也会使对话框无法依赖触摸滚动。
- **建议动作：** 删除 body 上的 `touch-action: none`，只保留 Canvas；控件与对话框使用浏览器默认触摸行为。
- **优先级：高｜必须改**

### 4.4 横屏小屏对话框缺少滚动边界

- **现象：** `dialog` 没有 `max-height` 和 `overflow: auto`，内容接近或超过手机横屏高度。
- **影响：** 关闭、分享或配色控件可能落到可视区域外；body 又禁止滚动时尤其严重。
- **建议动作：** 给 dialog 设置基于 `100dvh` 的最大高度和内部滚动，并在真机横屏验证安全区。
- **优先级：高｜必须改后再接受“双端同等支持”**

### 4.5 键盘和焦点基础实现良好

- **现象：** 控件均为原生元素，`target.closest(...)` 避免 Space/Enter 同时激活控件和发射；dialog 关闭后焦点回到编辑按钮；焦点样式覆盖按钮、输入框和 textarea。
- **影响：** 没有自制控件或 Canvas 命中测试，键盘模型简单可靠。
- **建议动作：** 保持当前结构，只补重播后的焦点实测。
- **优先级：低｜当前正确**

## 5. 代码与工程

### 5.1 模块边界守住了，不要继续抽象

- **现象：** `main.ts` 只读取 `world.blasts/view/phase`，没有直接操作 `world.particles`；粒子变换都在 `fireworks.ts` 内完成。
- **影响：** 页面流程与粒子实现仍然分离，同时没有 class、service、adapter 或状态机依赖。
- **建议动作：** 保持三个生产 TS 模块。`main.ts` 414 行、`fireworks.ts` 645 行目前仍按职责成块可读，不值得拆 renderer/audio service。
- **优先级：低｜当前正确，无需改**

### 5.2 `World` 的封装靠约定而非类型，但当前足够

- **现象：** `World` 导出了 `particles` 等可变字段，理论上 main 可以修改；实际没有这样做。
- **影响：** 类型层面不完全封装，但改成 class、私有字段或大量 getter 会显著增加代码。
- **建议动作：** 保持约定即可。只把 spec 的 `readonly blasts` 改成“main 只读”，避免文档声称了实现不存在的类型保证。
- **优先级：低｜当前设计更简单**

### 5.3 只有场景测试不足以保护粒子生命周期

- **现象：** `scene.test.ts` 的 12 项覆盖很好，但复杂度最高的 `launch → update → explode → cap → reset` 没有永久测试；当前仅靠临时脚本和浏览器验证。
- **影响：** `heardBlasts`、重置、寿命、计数和上限类回归很容易再次出现。
- **建议动作：** 增加一个无框架的 `fireworks.test.ts`，只测确定性 RNG、七枚火箭最终爆炸、上限和 reset。不测试 Canvas 像素，也不引入 Vitest/Playwright。
- **优先级：中｜可以更好，建议加入**

### 5.4 静态检查健康

- **现象：** TypeScript/LSP 无错误；只有 `delete optional property`、嵌套三元和类型推断提示。
- **影响：** 都不是运行时或维护性阻塞项。
- **建议动作：** 不为消除这些提示改代码。`delete targetX/targetY` 在这里语义直接，嵌套三元也局限在三行 clamp。
- **优先级：低｜无需改**

## 6. 部署与安全

### 6.1 CSP 当前有效且没有过严

- **现象：** 线上返回 `script-src 'self'`、`style-src 'self'`，构建产物无内联 script/style；动态配色用 `style.setProperty()`。线上产物与本地 `dist` 字节一致。
- **影响：** Vite 外部脚本、CSS 和本地字体正常加载，没有 `'unsafe-inline'`，安全边界合理。
- **建议动作：** 保持。`connect-src 'self'` 当前略宽但风险很低；若追求最小权限可改为 `'none'`，不是必要项。
- **优先级：低｜当前正确**

### 6.2 缓存策略正确

- **现象：** HTML 为 `max-age=0, must-revalidate`；哈希资产一年 immutable；未哈希字体一天。
- **影响：** 新版本入口及时刷新，静态资产可长期缓存，字体更新最长延迟一天。
- **建议动作：** 保持。无需为了一个 896 字节字体引入带哈希复制流程。
- **优先级：低｜当前正确**

### 6.3 `X-Robots-Tag: noindex` 符合当前产品定位

- **现象：** 页面不进入搜索索引。
- **影响：** 有利于私人祝福体验，但牺牲公开搜索曝光。
- **建议动作：** 当前保留；只有以后将它变成公开作品展示页时再移除。
- **优先级：低｜当前正确**

### 6.4 Fragment 隐私说明：设计诚实，README 过度绝对

- **现象：** Design 明确说 Fragment 不发送给 Cloudflare，但会暴露给聊天软件和收件人；README 只说“没有后端，也不上传任何内容”。
- **影响：** README 容易让用户误以为祝福经过加密或不会被分享平台读取。
- **建议动作：** README 改为：“应用代码不上传祝福；Fragment 不随 HTTP 请求发给本站，但完整分享链接对聊天平台和收件人可见。”
- **优先级：中｜必须修正文案**

### 6.5 线上静态部署本身验收通过

- **现象：** 本地与线上 HTML、JS、CSS、字体逐字节一致；线上 CSP、安全头和缓存头均生效。
- **影响：** 没有“本地改了但线上还是旧版本”的漂移。
- **建议动作：** 无。
- **优先级：低｜当前正确**

## 7. 文档一致性与命令

### 7.1 Design 与 Spec 的揭示时长已经基本同步

- **现象：** Design 把 3.2s 定义为可微调基线；Spec 已记录 `k=26` 和实测约 3.85s。
- **影响：** 这不是未记录的实现漂移。
- **建议动作：** 若加入硬截止时间，再把最终上限同步到 spec。
- **优先级：低｜当前正确**
