# ASCII Firework 实现规格：每字粒子预算与长祝福（Spec v4）

> 状态：可实施。本文数值（`PER_GLYPH_BUDGET` / `TEXT_HARD_CAP` / `DECOR_FLOOR`）为**未验证基线**，
> 经 §8 真机与视觉矩阵后回写并更新状态行。
> 起因（产品决策，记录备查）：祝福长度限制从「总字符数」改为「每字 ASCII 粒子数上限」，

> 本文 §5 给出有界的数学论证而不是无限放行。

## 2. 现状核对（调研结论）

### 2.1 总字符上限的真实来源

- `MAX_CHARS = 60` / `MAX_LINES = 3` 定义于 `scene.ts:6-7`，在 `main.ts:49` **重复定义**，
  并写死在 `index.html:30` 的 label 与 `#counter` 文案里。
- 60 不是性能数，是排版数：手机安全区（390×844 → safeW 335px）3 行 × 20 字，
  字号刚好顶到 `SIZE_MIN = 16px` 下界。性能侧彼时只有 ~120 个文字目标，远低于预算 990。
- 真正随长度缩水的是**每字密度**：预算 = 全局份额 990/352，`planCellScale` 放大单元
  （k ≤ 2.5）均匀稀释。桌面目测 20 字左右即开始稀释（raw ≈ 40 点/字 × 20 > 990×0.9）。

### 2.2 每字原始目标数的数学

每字原始目标数 ≈ 覆盖率 × (字号/单元宽)²。单元随字号缩放（`CELL_DIV = 12`，钳 7–12px），
所以该值近似与字数无关，峰值出现在中大字号（单元被 `CELL_MIN` 钳住）：
CJK 粗体覆盖率 ~0.4–0.5 → **raw ≈ 35–45 点/字**。8×8 = 64 个单元是 CJK 点阵可辨的经验下界，
也是单字目标的物理上界（单元铺满全覆盖）。字多时字号被排版压小，每字原始量跌到个位数
（200 字手机端 ≈ 1.3 点/字）。

> 2026-09 栅格收细（`CELL_MAX` 12 → 10、`CELL_MIN` 7 → 6）后 raw 峰值升到 **≈55–88 点/字**，
> 200 字手机端升到 ≈3.2 点/字；上面的 35–45 与 1.3 是收细前的基线，新取值见 §3.1 回写记录。

### 2.3 隐患：文字超额会挤死装饰粒子

`enforceCap`（`fireworks.ts:1679`）按**总粒子数**对 `world.cap` 算超额，
但只裁装饰、不裁文字/火箭。若文字点阵超过 `cap`（本规格允许到 4800 > 1800），
超额会把全部火花、尾迹乃至新爆炸立即裁掉。**提高文字预算必须与 §4.2 一起上线。**

### 2.4 外部调研依据

- URL 长度：现代浏览器支持极长（Chromium 实务上限 ~2MB），但跨聊天平台/代理/旧浏览器的
  通用安全惯例是 **URL 全长 ≤ ~2000 字符**（Stack Overflow #417142 及各家汇总的一致建议；
  Chromium url_display_guidelines 只约束展示不约束长度）。`m` 参数 percent-encode 后
  CJK 每字 ×9 → 200 字 ≈ 1.86KB 含其余参数，刚好在线内；全 emoji 情形（×12/字）会超线，
  现代浏览器仍可用，接受为已知边缘（§7 风险）。
- Canvas 文本粒子成本：`fillText` 逐粒子逐帧调用，成本随粒子数线性；静态文字的标准优化是
  落定后烘焙到离屏画布、每帧 `drawImage`（呼吸改为整层 alpha）。本轮**不实施**，留作 §9 升级路径。
- `Intl.Segmenter` 已有运行时探测与码点兜底（spec 03 §4.1），本规格不新增依赖。

## 3. 数据契约

### 3.1 常量（新值；★ = 未验证基线）

| 常量 | 取值 | 位置 | 语义与推导 |
| --- | --- | --- | --- |
| `MAX_CHARS` | `60 → 200` | `scene.ts`（唯一定义） | URL 分享安全线推导（§2.4）；同时在 §4.3 证明最小屏不溢出 |
| `MAX_LINES` | `3 → 8` | `scene.ts` | 显式行数与自动候选行数上限；8 行 × 16px × 1.35 = 173px ≤ 任意安全高 |
| `PER_GLYPH_BUDGET` | `64` ★ | `fireworks.ts` | 每字素目标数上限；覆盖大字号 raw 峰值（§2.2，≈55–88 点/字），短祝福不再被削平 |
| `TEXT_HARD_CAP` | `4800` ★ | `fireworks.ts` | 文字目标绝对天花板，语义是**性能护栏**不是质量旋钮；75 字以内不触顶 |
| `REDUCED_TEXT_HARD_CAP` | `512` ★ | `fireworks.ts` | reduced motion 档（= 640 × 0.8，给零星火花留余量） |
| `DECOR_FLOOR` | `320` ★ | `fireworks.ts` | 装饰粒子保底额度（1 火箭 + 尾迹 + ~170 爆发火花，§4.2） |
| `TEXT_SHARE` | 删除 | `fireworks.ts` | 被 `PER_GLYPH_BUDGET` / `TEXT_HARD_CAP` 取代 |

> 回写记录（2026-09 产品决策「继续提升单字 ASCII 密度」，实施后已部署）：
> `PER_GLYPH_BUDGET` 40 → 64、`TEXT_HARD_CAP` 2400 → 4800；配套 spec 03 §3 的
> `CELL_MAX` 12 → 10、`CELL_MIN` 7 → 6（中等/小字号也变密：大字号 +35%、16px 长祝福 +36%）。
> 三项均为**未验证基线的新取值**：§5 峰值 2720 → 5120，§8 真机帧时间与可辨性矩阵必须重测；
> `REDUCED_TEXT_HARD_CAP` 仍为 512（reduced 档 `world.cap = 640`，不得反超），
> 副作用是 reduced 档从 ≤12 字触顶变为 ≤8 字触顶（长祝福密度不变）。

- `main.ts:49` 的重复 `MAX_CHARS` **必须删除**，改为从 `scene.ts` 导入（消重）。
- URL 契约不变：`v=1`、键集合、`normalizeMessage` 规则全部保留；只是 `isValidMessage` /
  `clampMessage` 里的两个常量变值。旧链接（≤60 字 ≤3 行）在新版完全等价；
  新版生成的长链接在旧版上被裁到 60 字——单向兼容，接受并写入 README。

### 3.2 不变量（新增，实现后逐条自查）

- 文字目标数 ≤ `min(PER_GLYPH_BUDGET × 码点数, 对应档 TEXT_HARD_CAP)`，恒成立（含 resize 重采样）。
- 任意时刻 `particles.length ≤ max(world.cap, textCount + DECOR_FLOOR) + 在途火箭数`。
- 文字粒子与火箭仍永不参与 `enforceCap` 裁剪（spec 02 §3.3 不变）。
- 排版结果任一行在 `SIZE_MIN` 下宽度 ≤ safeW（§4.3 构造性满足）。

## 4. 算法

### 4.1 预算公式（`sampleTargets` 内一行替换）

```ts
const hardCap = world.reducedMotion ? REDUCED_TEXT_HARD_CAP : TEXT_HARD_CAP;
const budget = Math.min(PER_GLYPH_BUDGET * countCodepoints(lines.join("")), hardCap);
```

- 字数口径用**码点**（与 `MAX_CHARS` 一致），不新增依赖；ZWJ 簇会略高估预算，无伤（上限语义）。
- `planCellScale` 机制不变：超预算仍只许放大单元完整重生成，禁止抽稀（spec 03 §4.7）。
- 效果分区（推导见 §5）：短祝福每字密度不再被削平到低水位（上限 = `PER_GLYPH_BUDGET`）；
  长祝福字号小、raw 低，预算天然不触顶；天花板只在高分屏中长祝福触达。

### 4.2 `enforceCap` 超额公式（与 §4.1 同批上线）

```ts
const textCount = world.targets.length; // 文字粒子数恒等于落定+在途补字，上界即 targets.length
const cap = Math.max(world.cap, textCount + DECOR_FLOOR);
let excess = world.particles.length - cap;
```

- 裁剪规则不变（只裁装饰， oldest-first）；空祝福时退化为现状（`max(1800, 320) = 1800`）。
- 已知交互（接受）：文字超 `cap × DENSE_SHARE` 时尾迹按现有降级逻辑永久跳过——
  长祝福下这是想要的省帧行为，注释说明即可。
- `textCount` 用 `world.targets.length` 而非逐帧扫描计数：它是文字粒子的恒等上界（spec 02 §3.3）。

### 4.3 排版：候选行数与长行折行（`layoutTextLines`）

1. 显式 `\n` 照旧是硬断行，保留作者意图；显式行数 ≤ `MAX_LINES`（`clampMessage` 已切）。
2. **单条显式行**（无 `\n`）：候选行数从 1–3 推广到 1–`min(MAX_LINES, 字素数)`，
   评分/惩罚（cut ranks）与「取字号最大」逻辑不变；但只接受 **unclamped size ≥ `SIZE_MIN`** 的候选。
3. **长显式行折行**（新）：任一显式行在 `SIZE_MIN` 下超 safeW 时，用既有贪心断行
   （同 cut ranks 惩罚）折到每行都 fit。这同时修复现存的「单行 40+ 字溢出安全区」缺陷。
4. 若 2 的候选全军覆没（极端长句），用 3 的折行结果兜底。
   不溢出证明：最小屏（375×667，safeW 322）16px 每行 20 字；200 字 ≤ 8 显式行，
   折行后 ≤ 16 行 × 21.6px = 346px ≤ safeH 480。✓

### 4.4 编辑器与文案

- `index.html:30` label 改为「祝福（最多 8 行、200 字）」；`rows="3"` 保留（对话框可滚动）。
- `#counter` 逻辑不变（`还可写 N 字 / M 行`，N/M 随新常量）。
- 输入裁剪、IME 组合保护、200ms 防抖采样全部保留（spec 01 §6 / spec 02 §2.1）。

## 5. 性能论证（"字多了卡不卡"的有界回答）

峰值总粒子 = `max(cap, min(64n, raw(n), hardCap) + DECOR_FLOOR)`：

| 情形 | 文字目标 | 峰值总量 | 对比现状 1800 |
| --- | --- | --- | --- |
| ≤10 字（大字） | ≤ 640 | 1800 | 不变 |
| 中长祝福（24–75 字，高分屏且 raw ≥ 64/字） | ≤ 4800（触顶） | **5120** | ×1.9，唯一变糟区间 |
| 200 字（手机） | raw ≈ 370（`CELL_MIN` 6 后） | 1800 | 不变 |
| reduced motion 任意 | ≤ 512 | 640 | 不变 |

关键性质：天花板只在**高分屏 + 中长祝福**触达，而高分屏设备通常性能更强；
小屏手机字越多字号越小，raw 天然远低于天花板。不存在无界路径。
§8 真机矩阵对「5120 峰值」情形测帧时间；不达标走 §9 升级路径，不预先优化。
